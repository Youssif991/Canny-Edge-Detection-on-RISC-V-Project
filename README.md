# Canny-Edge-Detection-on-RISC-V-Project

[![Doxygen](https://img.shields.io/badge/docs-Doxygen-blue)](docs/html/index.html)

Canny edge detection pipeline in C++ targeting RISC-V Vector (RVV) acceleration, validated on `qemu-riscv64`. Full architecture and API documentation lives in the [Doxygen docs](docs/html/index.html).

## Prerequisites

- RISC-V GNU toolchain: `riscv64-unknown-elf-g++` (`--with-arch=rv64gcv --with-abi=lp64d`)
- `qemu-riscv64` user-mode emulator
- GoogleTest at `$(HOME)/googletest-installed`
- Doxygen 1.9.8

## Setup

```bash
git clone https://github.com/Youssif991/Canny-Edge-Detection-on-RISC-V-Project.git
cd Canny-Edge-Detection-on-RISC-V-Project
chmod +x toolchain-setup/*.sh
./toolchain-setup/main.sh
source ~/.bashrc
```

The setup script builds the RISC-V toolchain, QEMU, GoogleTest, and a Python venv in sequence.

## Phase 4: Compiler Optimization Sweep

The scalar Gaussian blur kernel (both spatial 5×5 and separable implementations) was cross-compiled with five optimization levels and benchmarked on `qemu-riscv64` at VLEN 128/256/512 to establish a baseline before RVV intrinsic work begins.

Optimization Flag |	VLEN |	Spatial Gaussian (ms) |	Separable Gaussian (ms) | Binary Size
-O0 | 128| 54| 28| 115K
-O0	|256 |	54 |	27 |	115K
-O0 |	512 |	53 |	28 |	115K
-O2 |	128 |	19 |	12 |	31K
-O2 |	256 |	19 |	10 |	31K
-O2 |	512 |	22 |	15 |	31K
-O3 |	128 |	16 |	12 |	30K
-O3 |	256 |	17 |	10 |	30K
-O3 |	512 |	16 |	11 |	30K
-Os |	128 |	22 |	13 |	26K
-Os |	256 |	21 |	14 |	26K
-Os |	512 |	20 |	12 |	26K
-Ofast |	128 |	16 |	33 |	30K
-Ofast |	256 |	16 |	33 |	30K
-Ofast |	512 |	16 |	33 |	30K

**Observations:**
- `-O0` is roughly 3× slower than any optimized flag and produces the largest binary — expected, since it disables nearly all compiler optimization passes.
- `-O3` and `-Ofast` give the best runtime, edging out `-O2` slightly, with identical binary size.
- `-Os` trades binary size for speed less favorably than expected here: it's smaller than `-O0` but not smaller than `-O2`/`-O3`/`-Ofast`, while still being the slowest among the optimized flags.
- The separable Gaussian implementation consistently outperforms the spatial 5×5 convolution across every flag, confirming the expected algorithmic advantage (O(n) vs O(n²) per pixel for a 5×5 kernel).


🔍 Auto-Vectorization Diagnostic Analysis (GCC vs. Clang)

To fully understand why -Ofast and -O3 reached their optimization ceiling, we analyzed the auto-vectorization reports generated by both GCC 13 and LLVM Clang. These reports reveal how compilers interpret our scalar loops targeting the RISC-V Vector Extension (RVV) hardware.
1. GNU GCC 13 (-fopt-info-vec-all)

GCC adopted a highly conservative approach, missing the vectorization of core image-processing loops due to strict memory safety checks.

    Memory Clobbering & Allocation (statement clobbers memory): GCC refused to vectorize loops containing heap allocations or standard library functions (e.g., aligned_alloc and free in include/utils.hpp). It conservatively assumed these operations disrupt uniform data flow, leading to Analysis failed with vector mode DI.

    Exception Handling Constraints (statement can throw an exception): Vectorization was disabled in loops invoking functions that might throw exceptions, as GCC prioritizes safe control flow over SIMD parallelization.

    Type Ambiguity (no vectype for stmt): In src/magnitude.cpp, GCC struggled to map specific floating-point operations to native RVV vector types, falling back to scalar instructions entirely.

2. LLVM Clang (-Rpass=loop-vectorize)

Clang demonstrated a much more aggressive and capable auto-vectorization strategy, particularly adept at utilizing scalable RVV instructions.

    Vectorization Success (VLA Validation): Clang successfully recognized and vectorized the core row and column processing loops in src/gaussian.cpp (Lines 55, 141, and 150). It generated instructions utilizing scalable vector widths (vscale x 4 and vscale x 8), providing empirical proof that the architecture successfully leverages Vector Length Agnostic (VLA) capabilities.

    Cost Model Rejections (not profitable): In several instances (e.g., small or non-consecutive loops in src/gaussian.cpp), Clang correctly analyzed the loop overhead and concluded that interleaved vectorization was computationally more expensive than sequential execution (the cost-model indicates that interleaving is not beneficial).

    Remaining Aliasing Hurdles (cannot identify array bounds): In src/magnitude.cpp and src/sobel.cpp, Clang halted vectorization. It could not mathematically prove at compile-time that the source (row_top) and destination memory buffers do not overlap (Pointer Aliasing), safely falling back to scalar code to prevent data corruption.

Conclusion:
While compilers can partially auto-vectorize standard loops (as seen with Clang), complex image kernels (like Sobel and non-maximum suppression) suffer from pointer aliasing fears and branching constraints. This firmly justifies the necessity for explicit RVV intrinsic programming in the upcoming phases to force hardware-level SIMD parallelism.
